# JARVIS Builder Subsystem Read-Only Audit

## Executive Summary
The target packages (`builder/`, `mutant/`, `mutation/`, `evolution/`, `genome/`, `validation/`, and supporting nervous system ones) implement an **isolated, highly-structured but entirely deterministic proof-of-concept** of the developmental loop. 

**Zero classes in these packages are instantiated or called by the live `JarvisEngine` or any tracked production code.** Every integration is isolated within unit tests (e.g., `ToolBuilderTest`). All of these packages currently exist completely outside git source control (`Untracked files`).

100% of the tested functionality passes natively in the JVM environment (verified by build artifacts from `2026-08-22`), but the "candidate synthesis" relies exclusively on hard-coded stub implementations for 5 mathematical/string operations. No LLM or code-generation engine is present. The loop operates successfully but only on toy problems.

---

## 1. `builder/`
* **What it implements:** The front door for closing capability gaps (`ToolBuilder`). It accepts a `ToolSpecification`, runs static validation validation (`ToolValidator`), asks `CapabilityGapDetector` if the capability already exists, and executes a full `EvolutionEngine` generation loop if not. 
* **Real code quote:** 
  ```kotlin
  // ToolBuilder.kt:95
  val run = evolution.evolve(
      parent = parent,
      requirement = spec.toRequirement(),
      mutateFirst = true
  )
  ```
* **Production Status:** **Not instantiated live.** Never called by the production app. Called exclusively in `ToolBuilderTest`.
* **Loop Status:** Real implementation of the integration layer, correctly stringing the downstream phases together.

## 2. `genome/`
* **What it implements:** The declarative identity of a system. Stores metadata, inputs/outputs, latency/resource budgets, benchmark definitions, and lineage history. Features `GenomeArchive` for appending all generated instances to persistent disk storage (using `FileStorage`), and `GenomeRegistry` for pointing to the "current best" for a capability.
* **Real code quote:** 
  ```kotlin
  // GenomeArchive.kt:36
  fun put(genome: Genome) {
      store[genome.id] = genome
      _latestId.value = genome.id
      persistAsync()
  }
  ```
* **Production Status:** **Not instantiated live.**
* **Loop Status:** Real. Fully implements the `lineage` requirement described in the vault, storing full parent lineage and health states (`HEALTHY`, `TESTING`, `REJECTED`).

## 3. `evolution/`
* **What it implements:** The actual workflow orchestrator (`EvolutionEngine`). It executes candidate generation, sets up environments, iterates over baseline tests / failures tests, pushes candidates through the `PromotionGate`, and either discards them or uses the `PromotionController` / `RollbackController` to mutate system state atomically.
* **Real code quote:** 
  ```kotlin
  // EvolutionEngine.kt:169
  val decision = gate.decide(evaluation, regressionTests, resource)
  ```
* **Production Status:** **Not instantiated live.**
* **Loop Status:** Real orchestration of the `build -> test -> benchmark -> promotion gate`, but the "generation" piece (`CandidateGenerator`, `SpecSynthesizer`, `BehaviorSynthesizer`) is **heavily stubbed**. Candidates are *not* generated by an LLM; the engine simply hands back hard-coded logic for `clamp`, `normalize`, `invert`, `reverse_words`, or `lookup`:
  ```kotlin
  // SpecSynthesizer.kt:105
  is Behavior.Clamp -> "clamp(v, ${behavior.min}, ${behavior.max})"
  ```

## 4. `mutation/`
* **What it implements:** The `MutationEngine` to fork child genomes, the `FitnessModel` multi-dimensional Pareto scoring, and the `EnvironmentFactory` interface to produce physical runtimes (using a pluggable `EnvironmentBackend`). 
* **Real code quote:** 
  ```kotlin
  // FitnessModel.kt:149
  correctness = (passed.toDouble() / total),
  reliability = ((total - failures).toDouble() / total),
  latency = 1.0 - (avgLatency / 5000.0).coerceIn(0.0, 1.0),
  ```
* **Production Status:** **Not instantiated live.**
* **Loop Status:** Real. `FitnessModel` heavily implements the `score` evaluation logic. `EnvironmentFactory` correctly provides an abstract factory to scaffold isolated workspaces, but it's only backed by an in-process local executor.

## 5. `mutant/`
* **What it implements:** The physical `ResourceSandbox` that guards test executions with blocking timeouts, the `MutantEnvironment` which manages test case input/output mapping against generated code, and the `ProcessLocalBackend` which behaves as the local execution proxy for the "code".
* **Real code quote:** 
  ```kotlin
  // ResourceSandbox.kt:41
  val future: Future<SpecOutput> = executor.submit<SpecOutput> { spec.execute(input) }
  val output = try {
      future.get(timeoutMs, TimeUnit.MILLISECONDS)
  } catch (t: TimeoutException) {
  ```
* **Production Status:** **Not instantiated live.**
* **Loop Status:** The `isolated-workspace` requirement is primarily simulated. Although `EnvironmentFactory` creates unique `/tmp/candidate_X` directories and `ArtifactManager` correctly writes the "generated" files to disk, the `ProcessLocalBackend` never invokes a real interpreter or compiler. The "code" is just a Kotlin closure passed into `DeterministicSpec`. It simulates time crashes well but doesn't do real containerization. 

## Missing Pieces from the Vault Loop
* **Observe / Diagnose / Repair:** These steps are entirely missing. If a generated candidate fails tests, its score is lowered and it is rejected or set for re-mutation (`GateVerdict.MUTATE`), but there is **no LLM analysis (diagnose)** of *why* it failed, nor any prompt refinement (repair). It merely throws the result away and loops.
* **LLM Synthesis Engine:** `SynthesisProvider` is fully declared but unused for code generation. The multi-hybrid (`Deterministic`, `Cached`, `Heuristic`) providers just wrap hard-coded math boundaries via `BehaviorSynthesizer`.
* **Live Integration:** None. All of these packages are in `Untracked files` state to Git and live fully partitioned off from the active pipeline.
