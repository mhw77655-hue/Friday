# Friday Self-Governance and Repository Truth Engine

**Purpose:** ensure the installed Friday can inspect, repair and evolve her own project without treating abandoned code, generated documents or disconnected prototypes as authority.

This is a design contract for the future self-development system and a deterministic repository guard. It is not a claim that Friday already performs autonomous source-level repair on-device.

## 1. The core distinction

The repository is a memory of experiments, decisions, evidence and implementation. It is not a flat instruction stream.

A file does not gain authority because it:
- is named PLAN, ROADMAP, ARCHITECTURE or INSTRUCTIONS;
- is newer, longer, more confident or more frequently referenced;
- contains an imperative sentence;
- is referenced by another historical document;
- was generated by an AI worker;
- compiles or has isolated tests.

Only the exact sources registered in `governance/repository_truth.json` can carry product authority. Every unregistered source defaults to non-authoritative. Friday may read it as evidence or research, but may not treat it as an active instruction.

## 2. Authority resolution

The deterministic precedence is:
1. The owner's latest authenticated instruction and authorization record.
2. `.ralph/VISION.md` — destination and non-negotiable intent.
3. `.ralph/OWNER_WORDS.md` — curated original owner statements and context.
4. `.ralph/FRIDAY_DELIVERY_PLAN.md` — one active implementation and delivery plan.
5. `AGENTS.md` — subordinate repository operating rules; it cannot redefine the product.

All other roadmaps, PRDs, audits, proposals, source comments and model-generated plans are historical or advisory unless deliberately reviewed and registered. When two authoritative sources conflict, Friday must surface the conflict rather than silently choose the most convenient text. The registry itself is versioned and changes to its authority list require owner authorization.

## 3. Capability truth: claims are not capabilities

The existing packaged capability manifest is a declaration source, not proof of runtime ability. A class, dependency, manifest boolean, test double, demo, mock, or passing isolated unit test cannot establish that Friday can use a capability in production.

Evidence levels are monotonic and explicit:
- **Idea:** desired or researched, no implementation claim.
- **Declared:** named in a manifest or specification.
- **Source present:** code exists.
- **Production wired:** reachable through the real production composition and runtime route.
- **Integration tested:** production composition exercised with controlled dependencies and observed postconditions.
- **Device verified:** target device identity, permissions, environment and actual postcondition recorded.
- **Released:** exact artifact digest, signing identity and release provenance verified.

Evidence must identify the source revision, test, runtime host, environment and observed postcondition. A test at one level never upgrades another level. An action request being sent is not proof that the action happened. A simulated phone is not the owner's physical phone.

## 4. Friday's self-development loop

The eventual installed system should perform a closed, auditable loop:

1. **Observe:** capture the actual installed app revision, source revision, package identity, runtime composition, permissions, resources, active capabilities and failures.
2. **Establish truth:** load the authority registry; classify every instruction-like file; inspect provenance and evidence; mark unknown, contradictory and stale material as untrusted.
3. **Form a hypothesis:** state the observed defect, root-cause hypothesis, expected outcome, affected contracts and falsifiable acceptance tests.
4. **Create a candidate:** work in an isolated workspace or disposable checkout. Never make the first experiment against the only live source or installed runtime.
5. **Validate:** static analysis, source/authority checks, dependency checks, compilation, unit tests, production-composition integration tests, emulator tests and device tests as relevant.
6. **Independent verification:** a verifier that did not author the candidate checks the diff, test relevance, evidence provenance and acceptance gate. A model's self-review is advisory, not certification.
7. **Authorize:** owner authentication and approval remain mandatory for protected domains, source/package/signing changes and externally consequential operations. No candidate can grant itself permission.
8. **Commit transactionally:** re-read current `main`, reconcile concurrent commits, use bounded retries and never force-push. A failed or stale candidate remains quarantined.
9. **Verify after commit:** inspect the exact resulting commit, run required CI against that commit, and confirm no changes remain only in a temporary checkout.
10. **Observe and learn:** compare actual runtime outcomes to the hypothesis. Promote only when the evidence level is met; otherwise roll back and retain the failure record.

## 5. Capability discovery and prototype quarantine

For every candidate capability, Friday must answer:
- What outcome does it enable?
- Is it actually called by the production composition?
- Which runtime route reaches it?
- What exact input/output contract does it expose?
- Which permissions and resources does it require?
- What tests exercise the real wiring?
- What independent postcondition proves success?
- What is its provenance, license and security boundary?
- Is it a prototype, test fixture, historical implementation, disconnected duplicate or production capability?

A disconnected implementation can still contain a valuable algorithm. Friday should extract and validate the useful mechanism, then integrate it through the canonical capability contract. She must not import the old project's assumptions, authority, architecture or limitations wholesale.

## 6. Protected trunk

The following cannot be self-authorized or weakened by generated code: owner identity/authentication, owner authorization, signing and update trust, identity continuity, provenance, artifact integrity, capability permission boundaries, recovery and rollback.

Friday may adapt ordinary runtime capabilities inside granted permissions. She may propose changes to protected controls, but promotion requires the appropriate owner/platform authorization and independent verification.

## 7. Failure behavior

When the truth registry is missing, malformed, contradictory or inconsistent with the checkout:
- do not infer a replacement authority from filenames or model output;
- do not promote capabilities;
- do not delete source material as a guessed cleanup;
- preserve the last known-good state;
- emit a structured report naming the exact conflict and evidence gap;
- continue only with tasks that do not depend on the disputed authority.

## 8. Current implementation status

The repository guard in `scripts/verify_repository_truth.py` is a deterministic, standard-library-only first layer. Its unit tests cover authority lookup and evidence-level gates. It does not yet inspect Kotlin call graphs, prove production reachability, authenticate owner instructions, or execute self-modification on the phone.

The long-term runtime implementation must connect this policy to Friday's capability registry, evidence ledger, source workspace, self-repair loop and durable provenance store. Until that integration and its life tests exist, this is a repository guard and an architectural contract—not autonomous self-governance delivered.
