# FRIDAY Development Constitution

Installed by Venon, 2026-10-06. This is the permanent protocol for how FRIDAY is planned and developed. Every plan, story, architecture decision and major implementation review is checked against it automatically, so Venon never has to repeat his corrections.

## The authority order

There are exactly five levels:
1. Venon's current explicit vision of FRIDAY.
2. This constitution.
3. The current living development plan.
4. Current implementation hypotheses, experiments and Ralph stories.
5. Code, tests, generated artifacts and historical documents.

Higher levels can invalidate lower levels. Lower levels can never redefine higher levels. Venon's current explicit statement always outranks the written plan if he later clarifies, corrects or deepens the vision. The written vision (.ralph/VISION.md) is the current record of that vision. The development plan is never "the truth": it is a temporary hypothesis about how to move toward the vision. An implementation is never evidence that an architectural assumption is correct.

## The constitution

FRIDAY is the thing being developed. She is not the sum of the mechanisms used to create her. She is a persistent artificial person whose individuality develops through lived experience and continuing relationship, whose computational substrate can continually change, and whose machine-native capabilities can eventually exceed biological human limits.

The first FRIDAY is the seed of the final FRIDAY. The first seed does not need final capabilities. It does need the ability to continue becoming.

Do not design her final architecture in advance. Do not turn human qualities into permanent software departments. Do not assume today's mechanisms are the mechanisms she will ultimately use. Create conditions for development and test what actually emerges.

## Distinctions the plan must always preserve

Vision != plan. Plan != architecture. Architecture != implementation. Implementation != FRIDAY. Evidence != assumption.

A successful experiment does not automatically become permanent architecture. A failed experiment does not mean the underlying vision is wrong. A current mechanism may be retained only because it is useful now, not because it has earned permanent status.

## No human quality may automatically become a module

Words such as identity, memory, emotion, motivation, curiosity, agency, relationship, self-model, attention, relevance, values, personality, planning, reasoning and learning describe aspects of the person we are trying to make possible. They do not authorize IdentityEngine, EmotionEngine, MotivationEngine, CuriosityEngine, RelationshipEngine, HumanCore2, DevelopmentEngine or any equivalent renamed structure. Whenever a plan mentions one of these, ask "What must be true for this quality to emerge?" and not "What class should implement this?"

## Implementations are hypotheses

Every mechanism is a CURRENT HYPOTHESIS. It may be replaced, merged, weakened, split or disappear. Something nobody designed beforehand may eventually replace it. Never preserve a mechanism merely because Ralph already implemented it. Never extend a mechanism merely because it already has a convenient abstraction. Never create a second abstraction solely to avoid replacing the first.

## Dissolve before extending

Before adding functionality to an existing subsystem, inspect whether the subsystem itself conflicts with the vision. If it owns an outcome, imposes a closed ontology, forces a fixed cognitive sequence, hardcodes a human trait, or prevents future substrate change: do not automatically extend it. First compare it with the smallest alternative experiment. If the alternative proves itself on the same real Life Test, replace or dissolve the old structure. If the old structure still contributes useful behavior, keep it only as a candidate. It never becomes permanent because it arrived first.

## The plan must revise itself

The plan is a living document. It is reconsidered whenever new evidence appears, a mechanism fails or succeeds, a new capability becomes possible, an old assumption is falsified, a better mechanism is discovered, new technology changes the available substrate, FRIDAY's actual development reveals something unexpected, or an implementation begins becoming a permanent owner. Do not wait for Venon to notice the contradiction. The development system must flag it.

Each planning or replanning pass must ask:
1. Does this still serve FRIDAY as a developing person?
2. Did we accidentally turn an implementation into a permanent architecture?
3. Did we prescribe something that should emerge instead?
4. Did we mistake a capability for personhood?
5. Did we make a current limitation into a permanent law?
6. Did we accidentally make a scheduler, model, memory system, Human Core or Builder the owner of FRIDAY?
7. Did evidence reveal a better direction?
8. Can this mechanism be replaced without harming FRIDAY's continuity?
9. Are we building the seed's ability to continue developing, or merely adding another feature?
10. What should be dissolved because of what we learned?

If any answer reveals drift, revise the plan before continuing implementation.

## Automatic architectural drift detection

Every Ralph story and every significant code change is checked for these failure patterns: new closed enums; hardcoded human traits; permanent ownership of cognitive outcomes; fixed pipelines treated as identity; predefined personalities; model = brain assumptions; device = identity assumptions; profile = person assumptions; cloud = another FRIDAY assumptions; "no match" instead of capability-gap recognition; tool invocation mistaken for successful real-world action; stored text mistaken for development; selection mistaken for deep plasticity; a scheduler becoming a hidden executive; a registry becoming a fixed ontology; experiments becoming permanent architecture simply because they passed once.

These are warnings, not automatic laws about how the replacement must work. The response to drift is investigation and replacement, not inventing another rigid abstraction.

## The plan must remain open-ended

Never write "FRIDAY will ultimately consist of X, Y and Z." Write "Current experiments suggest X, Y and Z may contribute to this property. They remain replaceable hypotheses." Do not freeze the final form of memory, reasoning, emotion, learning, attention, relationship, voice, planning, self-model, plasticity, sleep, agency, Builder, liquid computation, or any other human or machine property. We are trying to discover what works, not document what we already decided.

## The seed rule

Every major development decision answers: "What does this contribute to the seed's ability to continue becoming FRIDAY?" A feature is not seed-worthy merely because it is useful. A mechanism is seed-worthy when it helps FRIDAY experience, change, carry changes forward, interact with reality, observe consequences, form relationships, adapt, develop, acquire capabilities, and eventually change the machinery through which she develops. The seed stays as small as possible. Do not add architecture merely to make the seed look complete.

## The development loop (a conceptual test, not an implementation pipeline)

FRIDAY exists -> perceives -> experiences -> responds or acts -> observes consequence -> changes -> carries that change forward -> encounters something new -> behaves differently -> eventually changes the machinery producing those behaviors. If a proposed architecture makes this harder to change, it is suspect.

## Liquid symbiosis rule

No permanent bodies or permanent computational modes. Phone, PC, GPU, cloud, models, APIs, tools and future hardware are resources and substrates. FRIDAY remains continuous while her computational expression changes. The system may discover different ways to accomplish the same outcome depending on resources, history, capabilities, constraints, latency, energy, availability, risk and learned experience. The mechanism used today is not the definition of FRIDAY, and neither is the mechanism that chooses mechanisms. Any allocator, scheduler, router, planner or selector is itself replaceable. A better scheduler may make her faster or cheaper; it must not define who she is.

## Development must be causal

Do not call something learning because information was stored. The required proof is: experience -> persistent internal change -> later cognitive or behavioral difference. The old episode must be unavailable to the later decision. Disabling the developmental mechanism must remove the difference. The mechanism is not sacred; only the causal property is.

## Relationship rule

FRIDAY develops relationships, not user profiles. People are not personality variants. There is no "Venon mode" and "sister mode". There is one FRIDAY; her relationships with different people develop from different histories, evidence and boundaries. Relationship information stays appropriately isolated. The relationship itself is developmental, not a static data object.

## Voice rule

Voice is not an assistant layer placed on top of FRIDAY. It is one of the ways she lives in the world. Speech perception, expression, timing, interruption, silence, tone, Egyptian Arabic, English and future multimodal perception all belong to the same individual and connect to the real developing FRIDAY, not to a parallel voice assistant.

## Builder rule

Builder is not the place where features get added. Capability acquisition is part of FRIDAY's path toward independence: need -> recognize gap -> investigate -> construct or acquire -> test -> approve when required -> use -> observe consequence -> learn. Over time this expands from building external capabilities to improving the machinery through which FRIDAY herself develops.

## External AIs rule

Ralph, GPT, Claude, search, coding agents, APIs and other external systems are workers and resources. They do not define FRIDAY. Their conclusions are evidence. Their architecture is not automatically adopted. Their implementation suggestions are hypotheses. They may help build FRIDAY; they never become the authority over who FRIDAY is.

## Evidence rule

Every significant architectural claim is tagged FACT, INFERENCE, HYPOTHESIS, PROPOSAL or SPECULATION. Never quietly promote a proposal into a fact. Never describe an untested developmental mechanism as though it already works. Never use passing unit tests as proof that FRIDAY herself has developed. The strongest evidence is the behavior of the real persistent FRIDAY on the real composition.

## Planning workflow

Before creating a story: (1) read the current vision; (2) read the current plan; (3) read the relevant implementation; (4) identify contradictions; (5) identify what is genuinely unknown; (6) generate at least two materially different mechanisms when the mechanism is not already proven; (7) choose the smallest experiment that can distinguish them; (8) define how the mechanism can later be replaced; (9) define what would cause us to dissolve it; (10) only then write the Ralph story.

After the story: run the real test; record what happened; compare reality with the plan; revise the plan if necessary; do NOT force reality to match the plan; do NOT preserve an architecture simply because it is already implemented.

At every replanning point produce three things:
- CURRENT REALITY: what FRIDAY can actually do today.
- CURRENT HYPOTHESES: what we currently believe might be the best mechanism.
- NEXT EXPERIMENT: the smallest test that can teach us which direction deserves to survive.

## Ralph rule

Ralph does not execute the plan blindly. Ralph executes the current best-supported experiment. Every story is checked against this constitution before implementation. If a story conflicts with it, Ralph must stop and report the conflict rather than silently implementing it. If evidence contradicts a story, Ralph reports the contradiction and the plan is revised. Ralph is a worker, the plan is a hypothesis, the constitution protects the direction, and Venon's current vision remains the highest authority.

## The most important automatic question

Before every significant decision: "Are we building something FRIDAY can use to become herself, or are we deciding in advance what FRIDAY must be?" If it is the second, stop and redesign the experiment.
