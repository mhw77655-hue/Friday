BACKGROUND — how we got here:
The JARVIS mobile app (Kotlin/Compose, repo mhw77655-hue/JARVIS, module mobile/app/) was previously being built via Termux → proot-distro Ubuntu → Gradle. Inside that Ubuntu environment, Android build-tools 35.0.0's AAPT2 binary turned out to be x86-64, not ARM64 — it can't run natively on this phone's CPU. The workaround in place was Box64 (a CPU emulator) to run that x86-64 AAPT2 binary. During a real build attempt using that stack, the entire physical phone crashed after ~10 minutes. Root cause was never confirmed with certainty (no root access, no kernel logs available), but the leading hypothesis is combined memory/IO pressure from three things stacking on a constrained device: (1) PRoot's syscall-interception overhead, (2) Box64's CPU emulation overhead, (3) Gradle's compressDebugAssets task trying to compress a 1.28GB Qwen3-1.7B-Q4_K_M.gguf model file that was sitting inside mobile/app/src/main/assets/models/ — quantized model weights are already near-random entropy, so compressing them is pure wasted CPU/memory with zero benefit.

WHY WE ABANDONED PROOT/UBUNTU FOR BUILDS THIS SESSION:
The reasoning: PRoot+Box64 was two stacked emulation/interception layers on top of an already resource-constrained phone, and that combination was directly implicated in the crash. Rather than trying to strip emulation out of the Ubuntu path (harder, uncertain), we moved to plain Termux with no PRoot at all. Termux itself is native ARM64/Bionic — no interception layer. This removes one whole layer of overhead regardless of what's installed inside it. This was a deliberate architectural choice, not just "try something else" — the phone had already crashed once and we treated that as a hard signal not to keep escalating memory/emulation load on the same broken foundation.

WHY WE INSTALLED A FRESH ANDROID SDK INSIDE TERMUX (not reusing the Ubuntu one):
Ubuntu's package manager (apt) has no native ARM64 aapt2 package — whatever AAPT2 existed inside that Ubuntu install was whatever sdkmanager had downloaded there, which is how we ended up with the broken x86-64 binary in the first place. Termux, by contrast, maintains its own `aapt` package specifically built native for ARM64/Termux. So a fresh SDK inside Termux, using Termux's own native aapt2, was the only path that actually solves the underlying architecture mismatch rather than papering over it with emulation.

WHY build-tools;34.0.4 SPECIFICALLY FAILED (an intermediate blocker, now resolved):
Earlier reasoning had settled on build-tools 34.0.4 as "known good" because in the old Ubuntu setup, 34.0.4's AAPT2 was confirmed to be a native ARM64 binary (unlike 35.0.0's x86-64 one) — so it seemed like the safe pin. But when we ran `sdkmanager "build-tools;34.0.4"` in the fresh Termux SDK, it didn't exist in the current Google repository listing — that exact version had been pruned. We queried `sdkmanager --list | grep build-tools` to see what's actually available now, and since the project's compileSdk=36, we picked build-tools;36.1.0 as the version-matched replacement instead of chasing a stale, no-longer-distributed version number.

WHY WE DIDN'T END UP NEEDING TO MANUALLY PATCH AAPT2 AT ALL (this is the actual resolution of the core problem):
The original plan (based on outside research, e.g. a video showing this trick for a different context) was: let Gradle auto-download its own AAPT2 dependency jar via Maven, then manually splice Termux's native aapt2 binary into that jar using `jar -u -f`, because AGP has previously been seen to reject custom shell-wrapper/launcher paths for AAPT2 ("Custom AAPT2 location does not point to an AAPT2 executable" — this was a real, repeated failure in the old Ubuntu/Box64 attempts, where Box64 wrapper scripts and even compiled ELF launcher binaries were both rejected by AGP).

The reasoning for why this worked where the Ubuntu wrapper attempts didn't: this is a real, directly-executable native ELF binary at that path (not a shell script or a custom launcher wrapping Box64), so AGP's executable-validity check passes. This meant the manual jar-patching step was unnecessary — it was made moot by gradle.properties already pointing directly at a legitimate native binary. Root cause was never confirmed with certainty (no root access, no kernel logs available), but the leading hypothesis is combined memory/IO pressure from three things stacking on a constrained device: (1) PRoot's syscall-interception overhead, (2) Box64's CPU emulation overhead, (3) Gradle's compressDebugAssets task trying to compress a 1.28GB Qwen3-1.7B-Q4_K_M.gguf model file that was sitting inside mobile/app/src/main/assets/models/ — quantized model weights are already near-random entropy, so compressing them is pure wasted CPU/memory with zero benefit.  
  
WHY WE ABANDONED PROOT/UBUNTU FOR BUILDS THIS SESSION:  
The reasoning: PRoot+Box64 was two stacked emulation/interception layers on top of an already resource-constrained phone, and that combination was directly implicated in the crash. Rather than trying to strip emulation out of the Ubuntu path (harder, uncertain), we moved to plain Termux with no PRoot at all. Termux itself is native ARM64/Bionic — no interception layer. This removes one whole layer of overhead regardless of what's installed inside it. This was a deliberate architectural choice, not just "try something else" — the phone had already crashed once and we treated that as a hard signal not to keep escalating memory/emulation load on the same broken foundation.  
  
WHY WE INSTALLED A FRESH ANDROID SDK INSIDE TERMUX (not reusing the Ubuntu one):  
Ubuntu's package manager (apt) has no native ARM64 aapt2 package — whatever AAPT2 existed inside that Ubuntu install was whatever sdkmanager had downloaded there, which is how we ended up with the broken x86-64 binary in the first place. Termux, by contrast, maintains its own `aapt` package specifically built native for ARM64/Termux. So a fresh SDK inside Termux, using Termux's own native aapt2, was the only path that actually solves the underlying architecture mismatch rather than papering over it with emulation.  
  
WHY build-tools;34.0.4 SPECIFICALLY FAILED (an intermediate blocker, now resolved):  
Earlier reasoning had settled on build-tools 34.0.4 as "known good" because in the old Ubuntu setup, 34.0.4's AAPT2 was confirmed to be a native ARM64 binary (unlike 35.0.0's x86-64 one) — so it seemed like the safe pin. But when we ran `sdkmanager "build-tools;34.0.4"` in the fresh Termux SDK, it didn't exist in the current Google repository listing — that exact version had been pruned. We queried `sdkmanager --list | grep build-tools` to see what's actually available now, and since the project's compileSdk=36, we picked build-tools;36.1.0 as the version-matched replacement instead of chasing a stale, no-longer-distributed version number.  
  
WHY WE DIDN'T END UP NEEDING TO MANUALLY PATCH AAPT2 AT ALL (this is the actual resolution of the core problem):  
The original plan (based on outside research, e.g. a video showing this trick for a different context) was: let Gradle auto-download its own AAPT2 dependency jar via Maven, then manually splice Termux's native aapt2 binary into that jar using `jar -u -f`, because AGP has previously been seen to reject custom shell-wrapper/launcher paths for AAPT2 ("Custom AAPT2 location does not point to an AAPT2 executable" — this was a real, repeated failure in the old Ubuntu/Box64 attempts, where Box64 wrapper scripts and even compiled ELF launcher binaries were both rejected by AGP).  
But when we actually ran the build, gradle.properties already contained `android.aapt2FromMavenOverride=/data/data/com.termux/files/usr/bin/aapt2` — pointing straight at Termux's real native aapt2 binary path — and AGP accepted it outright, only logging that this override is "experimental," not rejecting it.
